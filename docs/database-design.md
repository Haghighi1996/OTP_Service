# Database Design

## Scope

This schema supports the Phase 2 OTP lifecycle: an OTP is issued for a phone
number, expires after a short period, and can only be used once. It deliberately
does not include tenants, API keys, Redis, or delivery jobs; those belong to
later phases.

## `otps`

| Column | Type | Purpose |
| --- | --- | --- |
| `id` | `BIGINT` | Internal, database-generated identifier. |
| `phone_number` | `VARCHAR(32)` | Recipient identifier in normalized E.164 form, validated by the application in a later phase. |
| `otp_hash` | `TEXT` | Hash of the OTP. Plaintext codes are never persisted. |
| `expires_at` | `TIMESTAMPTZ` | Absolute expiration time in UTC. |
| `used_at` | `TIMESTAMPTZ` nullable | Set when verification succeeds; `NULL` means unused. |
| `created_at` | `TIMESTAMPTZ` | Issue time, generated by PostgreSQL. |

The service can retain multiple historical rows for a phone number. This keeps
an audit trail and avoids a uniqueness constraint that would conflict with OTP
re-issuance. Later service and repository work will define how a newly issued
code invalidates or supersedes prior active codes.

## Integrity rules

- A phone number and OTP hash cannot be blank.
- An OTP must expire after it was created.
- A used timestamp cannot predate creation.
- `used_at` is the durable source of truth for one-time use. Verification will
  later update it atomically so concurrent requests cannot reuse a code.

## Indexes

- `idx_otps_phone_number_active_created_at` is a partial index over unused OTPs
  ordered by newest first. It serves the active send/verify lookup without
  indexing consumed history.
- `idx_otps_expires_at` supports a future retention cleanup job.
